# Eval-Hard · memcore 硬检索评测集

> 文件：`tests_eval_hard.py`（评测脚本 + 用例）／ 本文（口径、来源、基线）
> 数据：真实库 `~/.dsh/memory/memory.db`，**516 条**（快照时刻 2026-11-02 19:0x）
> 状态：37 条用例，四个类别各 ≥ 8 条；**全部 37 条在 top-5 内都能命中**，没有一条是"库里没有答案"。

---

## 1. 为什么需要这份尺子

`tests_eval.py` 的 12 条已经**饱和**，而且饱和发生在两个层面：

| 现象 | 数字 | 后果 |
|---|---|---|
| 老尺子顶格 | Recall@1 = 10/12、Recall@3 = 11/12 | 12 条里只剩 2 条有区分空间 |
| 加 40 条近期干扰项后 | additive MRR **0.881** vs multiplicative **0.880** | 换排序公式，指标不动 → A/B 测不出差异 |
| 检索层三处落地后（M00554） | 老尺子 **12/12、12/12** | 已经满格，后续任何排序改动都不再可见 |

所以这份评测集解决的是**分辨力**问题，不是"再多跑几条"。判据很简单：一条用例只有在
"换一版排序有可能改变它的名次"时才有价值；名次恒定第 1 的用例只用来防回归。

## 2. 数据来源与快照口径（重要）

- 库里是**真实长期记忆**：`memories(id, kind, title, body, tags, project, created_at,
  use_count, salience, …)`，516 条（episode 285 / artifact 118 / note 67 / insight 14 /
  fact 12 / preference 10 / decision 9 / identity 1）。
- 探索阶段用 `sqlite3.connect('file:…?mode=ro', uri=True)` 只读 dump 全库标题与正文，
  手工找"同主题簇"；候选 query 用 `Memory().search()` 逐条试，记录真实名次。
- **runner 默认走快照**：用 SQLite `backup()` API 把 `memory.db` 复制到临时目录再检索，
  连 `config.json` 一起复制（权重与候选上限必须和真库一致，否则测的不是同一套参数）。
  理由有两条，都是实测踩出来的：

  1. `search()` 命中沉睡条目会写 `wake_count/last_wake_at`（引擎的"被想起"语义）。
     评测天天跑，尺子不该自己去改被测对象的状态。
  2. **直接 `cp memory.db` 会丢数据**：WAL 模式下未 checkpoint 的事务在 `-wal` 里。
     实测：只拷 `memory.db` 得到 515 条（少 1 条），同一批用例从
     R@3 35/37 掉到 **30/37**、MRR 0.752→0.732。`backup()` 不会被这个坑坑到。
     顺带一个边界：缺 `-shm` 时 `mode=ro` 打不开 WAL 库（sqlite 需要写目录建 `-shm`），
     脚本会退到 `mode=rw`——只做共享内存映射，不改任何一行。

- 需要直连真库时用 `--live`（明知会写唤醒计数）。
- 稳定性实测：同一快照连跑 3 次，R@1/R@3/MRR 完全一致；`--live` 与快照在同一份数据上
  结果也一致（21/37、35/37、0.752）。**库在长**（写这份文档期间 515→516，M00554 是并发
  另一方写进来的新决策），所以基线必须连同"516 条"这个锚点一起引用。

## 3. 四类用例与判定标准

| kind | 类别 | 判定标准 | 条数 |
|---|---|---|---|
| `para` | 近义改写 | query 与目标记忆几乎不出现在同一措辞里（口语、指代、换主语）；正确答案仍是那一条，而不是字面最近的邻居 | 10 |
| `alias` | 跨语言 / 别名 | 用英文名、协议名、仓库名、文件名、用户口头叫法去找中文标题条目 | 8 |
| `time` | 时间错位 | query 带"最早/最后/后来/隔天/才要的"等时间线索；**正确项是时间上对的那条**，最相似的那条是错的 | 8 |
| `dist` | 干扰项 | 同主题 3~5 条相似记忆，只有一条是答案；`why` 必须写清其它条为什么不算 | 11 |

挑选纪律（先验证再入册）：

1. **答案必须真实存在**：目标 id 在库里，且我第一次就核对了它的标题/正文确实在回答这个问题。
2. **必须是"能检索到但排不对"**：所有 37 条在 `k=5` 内都能命中（21 条第 1、14 条 2~3、
   2 条第 4）。没有一条是"库里没答案"或"预期失败"——那是许愿单，不是尺子。
3. **干扰项要能点名**：每条 `why` 都写出相邻条目 id 与"为什么不算"，否则无法判断用例对错。
4. **标题兜底唯一性**：`expect_titles` 逐个在全库做过子串碰撞检查，只有两条会同时命中
   同一用户消息的重复条目（M00332/M00334、M00353/M00355），这两种情况在 `expect_ids`
   里都列全了，属于"同一问题的两个条目都算对"。

## 4. 标注格式

```python
{
    "q": "那晚最早问的是哪条自驾路线",
    "expect_ids": ["M00485"],              # 优先：精确 id
    "expect_titles": ["理小路自驾游路线"],   # 兜底：标题子串
    "kind": "time",                        # para / alias / time / dist
    "why": "四条自驾（理小路 01:57 / 贵州 02:06 / 云南 02:08 / 龙泉山日出 02:15）里最早的那条；…",
}
```

匹配顺序（`find_rank`）：先在**整个 top-k** 里找 `expect_ids`；一条 id 都没有时才回退
到标题子串。这样"排到第 4 的正确答案"仍然算命中（记入 MRR），不会被误判成未命中。

## 5. 怎么跑

```bash
python3 tests_eval_hard.py                  # 默认 k=5，快照模式（推荐）
python3 tests_eval_hard.py --k 10           # 放宽 k
python3 tests_eval_hard.py --json           # 机器可读（打分脚本/CI 用这个）
python3 tests_eval_hard.py --verbose        # 每条附带期望、理由、完整 top-k
python3 tests_eval_hard.py --live           # 直连真库（会写唤醒计数）
python3 tests_eval_hard.py --home /path     # 指定 MEM_HOME
```

- 输出：总体 `Recall@1 / Recall@3 / MRR` + **四个类别各一行** + 每条一行
  `[✓/·/✗] kind query → 实际 top1 标题 (名次)`。
  `✓` = 第 1；`·` = 进了 top-k 但没排第 1（可提升空间）；`✗` = 没命中。
- **退出码恒为 0**：这是量尺不是闸门；阈值判断交给 `--json` 的消费方。
- 只用标准库（`sqlite3 / json / argparse / tempfile / shutil`），不联网，不引第三方依赖。

## 7. 已知局限与使用纪律

1. **`pitfall` 标签有门控**：`search()` 里对带 `pitfall` 标签的雷区条目有一条硬规则——
   query 不含「坑/雷区/教训/踩过/preflight」就直接剔除。所以 #6、#9、#37 三条的 query
   自带「坑」字。这是引擎的现行契约（"雷区是关于记忆的记忆"），不是用例取巧；
   如果哪天改掉门控，这三条会立刻浮动，正好当哨兵。
2. **答案集有时包含重复条目**：#28（M00430/M00431）、#29（M00353/M00355）、
   #24（M00332/M00334 经标题兜底）是同一用户消息被记了两遍，两个都算对。
   这类条目也解释了为什么"会话回顾"经常抢占 top1——同一话题被 episode 再摘要一次。
3. **时间线索用序数而不是墙上时钟**：`最早/最后/后来/隔天` 相对的是**内容时间线**，
   库长到几周后语义不变；刻意不用"昨天/今天"这类会漂的说法（只有 #26 用了"今天早上"，
   若日后重跑出现漂移，把它改成序数说法即可，别改答案 id）。
4. **库在长，基线要带锚点**：本文基线对应 516 条、2026-11-02 19:0x。新增记忆（尤其
   episode）可能整体抬高一两个名次，比较时请引用同一锚点，或先 `mem gc --dry-run` 看库况。
5. **不写预期失败的用例**：`search()` 的词法通道是字符 trigram、语义通道是哈希 n-gram 余弦，
   整句英文去查纯中文标题时两路都没有公共 n-gram。实测 `the AI livestream implementation
   plan for the pet avatar` 这类 query，正确答案 M00052 在 top-5 里根本不出现（返回的是
   M00005/M00006 等其它条目，有结果但答案是错的）。这种 topic 不入册，换成"英文术语 +
   中文语境"的混写形式（如 `cEMI 报文那个模块`、`Graphiti 的 valid_at`），那才是真实用法。
6. **不改已有文件**：本次只新建 `tests_eval_hard.py` 与本文；`memcore.py`、`mem`、
   `server.py`、`tests/`、`tests_eval.py`、README 均未改动。
